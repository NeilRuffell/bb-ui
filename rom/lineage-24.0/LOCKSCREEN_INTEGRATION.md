# Integrating the BB6 lock screen into LineageOS 24

This document maps the BB UI prototype to a **native, rootless ROM change**.
The current development APK uses Vector/Xposed only to reach SystemUI.
A ROM build should **not** ship that instrumentation or recreate its hooks.

## Desired native composition

Build a keyguard presentation selected by the SystemUI keyguard state:

| State | UI owner | Native components |
|---|---|---|
| Interactive `KEYGUARD` | BB6 lock-screen presentation | BB6 header and app/count icons, genuine status indicators, emergency and safety information |
| `SHADE` or `SHADE_LOCKED` | Existing SystemUI shade | Native shared notification stack, QS and notification actions |
| `PRIMARY_BOUNCER` | Existing Android authentication | Native password/PIN/pattern, emergency access and error text |
| AOD / DOZING | Existing SystemUI AOD | Native clock, notification indicators and burn-in handling |
| Unlocked | Existing SystemUI | No BB6 lock-screen views |

A pure policy prototype is in `BB6NativeChromePolicy`; it has unit tests.
Preserve the native `KeyguardManager`, bouncer controllers, user authentication,
notification listener, notification ranking and shade handling.

## Native source locations and intended changes

All paths below are relative to `frameworks/base/packages/SystemUI` at
`lineage-24.0`. These are **integration guidance**, not an untested ready-to-flash
patch.

1. **Keyguard composition/blueprint.**
   Select a BB6-specific interactive lock-screen layout/blueprint, instead of
   adding an independent always-on overlay to
   `res/layout/super_notification_shade.xml`. Keep
   `KeyguardRootView`, the authentication container and the indication area.

2. **Clock.**
   `src/com/android/systemui/keyguard/ui/view/layout/sections/ClockSection.kt`
   binds clock face views through
   `src/com/android/systemui/keyguard/ui/binder/KeyguardClockViewBinder.kt`.
   In the BB6 interactive blueprint, **do not add/bind the stock lockscreen
   clock face views**. Let the BB6 header own the time. Keep the native
   ClockSection/Binder in AOD and non-BB6 compositions.
   `ClockViewIds` are generated by `View.generateViewId()`, not stable
   `R.id` constants; do not attempt to hide them by guessed XML IDs.

3. **Date without deleting weather.**
   `src/com/android/systemui/keyguard/ui/view/layout/sections/SmartspaceSection.kt`
   adds the date plugin as the first child of each date/weather group; the
   weather view follows at index 1. In the BB6 interactive blueprint, **omit
   construction of the date plugin** while retaining weather, alarm and DND
   elements if they are separately enabled. Avoid deleting the whole
   SmartspaceSection: it also owns useful nondate information.

4. **Carrier without deleting system indicators.**
   `src/com/android/systemui/keyguard/ui/view/layout/sections/DefaultStatusBarSection.kt`
   inflates `res/layout/keyguard_status_bar.xml`. The native carrier
   is `@id/keyguard_carrier_text`. Provide a BB6-specific keyguard header
   layout **without this label**, and adapt
   `src/com/android/systemui/statusbar/phone/KeyguardStatusBarView.java`
   and its controller/binder so absent carrier is supported. Preserve
   `status_icon_area` and signal, battery, privacy, airplane and emergency
   indicators; they are not duplicates of the BB6 operator label.

5. **Notification cards and stock notification icons.**
   The shared notification container is
   `@id/shared_notification_container` in
   `res/layout/super_notification_shade.xml`.
   Do not insert/bind the native notification-list section in the BB6
   interactive lock-screen composition. Keep it in shade composition;
   notification data must remain registered and available for the
   `BB6LockScreenHeader` app-icon/count row.
   `src/com/android/systemui/keyguard/ui/view/layout/sections/AodNotificationIconsSection.kt`
   adds `@id/aod_notification_icon_container`; omit that section from the
   BB6 interactive presentation, but retain it in AOD.

6. **Generic swipe instruction only.**
   `src/com/android/systemui/statusbar/KeyguardIndicationController.java`
   produces the generic `R.string.keyguard_unlock` message in
   `showActionToUnlock`. Do not schedule that default message while the
   BB6 interactive presentation owns keyguard. Keep authentication errors,
   biometric guidance, charging information, security warnings and screen
   reader/accessible descriptions.

7. **Keyboard entry.**
   Preserve `BB6KeyguardKeyboardHook`'s *behavior* natively: physical Space
   on the lock screen asks the OS's real primary credential presenter.
   Do not ship `XposedBridge`, Vector, or a replacement credential input.
   The Q25's optimized SystemUI currently exposes the native
   `(String reason, boolean scrimmed)` call order; when compiling a native
   ROM, call the source API as compiled in that ROM, not via reflection.

## Burn-in layer reference integrity (verified Q25 failure)

The 0.9.40 prototype crashed `com.android.systemui` repeatedly:
`AodBurnInLayer.transform()` attempted `View.getLeft()` on a null View.
The native `AodBurnInSection.kt` creates a persistent
`AodBurnInLayer` (`androidx.constraintlayout.helper.widget.Layer`) which
stores IDs of participating views, including dynamically created clock and
Smartspace views registered by the native binders.

For the temporary APK prototype, detaching a view must also unregister it
from the burn-in layer **before** detachment and register it **after**
reattachment. The layer always retains its required
`burn_in_layer_empty_view`. `AodReferencePolicy` rejects detachment when
the native reference API is missing or when removing a container would orphan
a referenced descendant. Unit tests enforce the fail-closed decisions.

In a **native ROM**, modify `AodBurnInSection`, `ClockSection`,
`KeyguardClockViewBinder`, `SmartspaceSection`, and
`KeyguardSmartspaceViewBinder` together with the BB6 keyguard blueprint.
When a stock clock/date view is **never created**, do not register its ID in
the burn-in layer or generate a constraint referencing it. This is the
proper source-level solution. Do not mask the crash by catching
`NullPointerException` in the native layout system.

## Development APK versus the final ROM

The test APK uses `BB6NativeLockscreenComposition` to **detach** redundant
View children from `KeyguardRootView` while BB6 owns interactive keyguard.
It stores each original parent, index and layout parameters, and restores
the same native children for AOD, native shade, bouncer and unlock. The native
shared notification subtree is detached and reattached similarly.
Nothing is made invisible or transparent as a substitute for removal.

That detachment is a **development-stage compatibility adapter**, not the
recommended ROM implementation. In LineageOS, construct the correct native
blueprint in the first place so no redundant views are inflated/bound in
the interactive BB6 composition.

## Validation before a ROM merge

Build the entire Q25 SystemUI/Lineage tree, not only `app:assembleDebug`.
Test fresh boot, cold lock, AOD, screen-off-to-screen-on, lock/unlock cycles,
active clock-face changes, native password/PIN/pattern, emergency calling,
notifications arriving and disappearing, locked and unlocked shade expansion,
SIM removed/airplane mode, accessibility indications, wallpaper changes and
landscape/rotation where supported.

An Android APK unit test or successful CI build **cannot** certify any of
those runtime transitions. Do not mark the ROM integration complete until
these tests pass on the target system image.
